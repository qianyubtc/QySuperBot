# 运行与部署

## 本地开发

`npm ci && npm run dev` 同时启动 NestJS 与 Vite。网页 `http://127.0.0.1:5174`，开发代理把 `/api` 转发到 3000。Ctrl+C 关闭两端服务，配置读取根目录 `.env`。

`npm run check` 包含类型检查、业务、数据库、协议以及只绑定本机临时端口的 HTTP 测试。`npm run build && npm start` 从构建产物启动。健康检查：`GET /api/v1/health`。

## Telegram 成员管理

Telegram 群详情新增“成员管理”，实时消息中的“管理”可带入成员 ID。网页支持限时禁言、封禁、记录／查询／清除警告；操作要求后台管理员会话、CSRF 与 `Idempotency-Key`。相同键与载荷只提交一次，变更目标或操作会冲突。警告为群级持久记录，清除只停用计数，不删除历史；当前不按累计次数自动处罚。网页警告只记录在后台，群内 `/warn` 还会发出公开提醒。

群内管理员命令默认关闭，在该群“成员管理”中单独开启。回复目标成员的一条消息后使用：

- `/mute 10m 原因`：限时禁言，支持 `s/m/h/d`，范围 60 秒至 30 天，仅限超级群。
- `/ban 原因`：封禁成员。Telegram 超级群会禁止重新加入并撤回该成员的消息；普通群不保证阻止重新加入。
- `/warn 原因`、`/warnings`、`/clearwarns 原因`：增加、查看与清除警告。

命令支持 `@机器人用户名`，忽略其他机器人、匿名发送者及超过一分钟的旧更新。仅接受群主或管理员；禁言／封禁还需命令发送者具有限制成员权限。收到错误命令时，已核实的管理员会得到“命令未执行”提示。群内通知沿用持久发送任务和话题、引用回复能力，提交提示不会冒充成功回执。

每条命令更新只尝试一次，包括已忽略或已拒绝的命令；重新投递不会因为之后提权或开启设置而补执行。处理中断后请重新发送命令。关闭管理员命令会取消待执行的群内命令任务；重新开启不会恢复旧任务。执行中的任务还会复查命令设置与同步范围版本。

提交与执行前核验机器人、目标及命令发送者的实际身份；保护群主、管理员、机器人及命令发送者本人。已有成员限制时拒绝追加禁言，以免覆盖人工限制。执行前再次检查账号暂停、同步范围、已知入群批次和 25 秒有效期；禁言固定结束时间，避免排队后意外变成永久限制。已有处理中或结果未知的成员任务时不再叠加处罚。明确拒绝显示失败，矛盾或缺失回执显示待核对，不自动重试。

禁言到期由 Telegram 原生处理。提前解除禁言、解封和组合踢出仍在 Telegram 客户端操作；当前没有宣称支持平台不提供的条件解除能力。新增数据库结构为 `conversations.management_settings`、`member_actions` 及其查询索引，不改变既有群规则。

接口：`GET /api/v1/conversations/:id/member-management?user_id=...` 查看状态；`PUT` 同路径保存 `{commands_enabled}`；`POST /api/v1/conversations/:id/member-actions` 提交 `{user_id,action,reason,duration_seconds?}`。所有入口仅限后台管理员，项目密钥不可调用。

依据：[Telegram 成员限制与封禁 API](https://core.telegram.org/bots/api#restrictchatmember)、[实时成员身份](https://core.telegram.org/bots/api#getchatmember)。

## 配置

| 环境变量                   | 默认 / 含义                                                                                              |
| -------------------------- | -------------------------------------------------------------------------------------------------------- |
| `HOST` / `PORT`            | `127.0.0.1` / `3000`                                                                                     |
| `PUBLIC_ORIGIN`            | `http://localhost:3000`，回调地址；应设为连接器能访问的真实地址                                          |
| `DATA_DIR`                 | `.local/data`，本地数据库和加密密钥目录                                                                  |
| `DATABASE_URL`             | 留空使用持久 PGlite；设置 PostgreSQL URL 后使用外部库                                                    |
| `SEED_DEMO`                | 默认 true，仅首次初始化演示数据；改 false 不删除已有数据                                                 |
| `ADMIN_SETUP_TOKEN`        | 初始化凭据；非回环地址必须配置，否则无法创建管理员                                                       |
| `COOKIE_SECURE`            | HTTPS 部署设 true；本机 HTTP 保持 false                                                                  |
| `ENCRYPTION_KEY`           | 64 位十六进制 AES 密钥；留空在数据目录生成 `master.key`                                                  |
| `ALLOW_PRIVATE_CONNECTORS` | 默认 false；连接本机/私网 QQ 或自有服务时显式设 true，链路本地地址仍拒绝                                 |
| `QQ_LOCAL_PORT`            | 可选；仅 QQ 连接可访问 `http://127.0.0.1:<端口>`，其他私网地址仍按默认策略拒绝；同机 NapCat 优先使用此项 |

密码用 scrypt 散列，平台凭据用 AES-256-GCM 加密，项目 Key 仅存散列。HttpOnly / SameSite=Strict 会话，写请求校验 CSRF。当前只有一个管理员，未提供网页密码修改/找回或密钥轮换。消息和审计持续保留，暂未实现自动清理。

## Telegram

1. 在 BotFather 创建机器人，添加到测试群并授予需要的权限。要读取完整群消息，关闭隐私模式或授予管理员角色。
2. 添加 Telegram 连接、填写 Token，点击“连接 / 刷新”。后台验证 Token、检查已有 Webhook 并拦截同一机器人的重复活动连接；不会自动删除 Webhook。
3. 轮询可发现新群事件，也可填写已加入的群/频道 ID。Bot API 没有通用的“列出所有群”接口，本版不会声称清单完整。
4. 群详情检查能力和权限，先观察，再启用自动处理。

每 3 秒短轮询，不补取接入前的完整聊天历史；Telegram 已排队的待接收更新可能在首次轮询到达。不会自动删除已有 Webhook。同一个 Bot 需选定唯一接收进程；已有 Webhook 或其他轮询器时会显示冲突。本版没有 Telegram Webhook 入口。机器人离群、被移除、被禁言、群限制普通成员发言或频道不允许发帖时，会拒绝发送；成员身份查询失败时权限保持未知。

删除、封禁与踢出分开。Telegram 支持删除与明确封禁，不自动执行“踢出但允许重入”的封禁/解封组合。QQ 移除调用 `set_group_kick`。成员处分需要可信的当前入群批次，否则要求人工处理；广告删除独立执行。

依据：[Telegram Bot API](https://core.telegram.org/bots/api)、[OneBot v11 API](https://github.com/botuniverse/onebot-11/blob/master/api/public.md)。

## QQ

后台支持 VPS QQ 扫码登录。服务器先部署本机 NapCat，并将 `QQ_LOCAL_PORT`、`QQ_WEBUI_PORT`、`QQ_WEBUI_TOKEN` 配置到服务环境；WebUI 只绑定回环地址。管理员在“添加连接 → QQ · VPS 扫码登录”打开窗口，用手机 QQ 扫码确认，再点击“连接此账号”。后台核对在线 QQ 身份，登记本机 API 与带独立签名密钥的事件上报，读取群列表。已有同一 QQ 连接会复用，保留密钥和同步群选择；一个本机实例同时登录一个 QQ。已有连接的“VPS 扫码登录 QQ”也可重登，暂停账号需明确点击“恢复并连接此账号”。此入口不会自动退出当前 QQ、重置设备或改为其他账号；账号不符时拒绝替换已有绑定。

二维码在管理员页面本地生成，不经第三方二维码服务。WebUI 凭据仅在服务器内使用；API 不返回 WebUI Token、管理凭据或桥接 Token。登录检查只读取状态，不自动恢复账号；写入、刷新二维码与快速登录需要管理员会话及 CSRF。QQ 仍要求在手机端确认扫码；账号限制或验证问题需在手机 QQ 中处理。

复用尚未绑定身份的本机连接时，先在数据库事务中固定当前 QQ，再配置桥接和发现群；并发的旧刷新不能覆盖已绑定身份。旧连接没有 API Token 时，会加密保存本机 API 凭据并配置接口认证；已有密钥保持不变，重连不会轮换。身份绑定和补齐接口认证均记录操作日志。

QQ 群详情新增“入群审核”，可按群开启“自动通过新的入群申请”，默认关闭。需有已确认的群主／管理员权限、在线账号和已启用同步范围；权限未知时不允许开启。开启后仅处理签名上报的普通入群申请，不自动接受邀请登录号加入其他群；黑名单成员、旧申请和已取消同步群不自动通过。关闭会取消尚未执行的审核，重新开启不补处理旧申请。

每个申请的凭据加密保存并去重，执行前再次核对登录 QQ、管理权限、范围／设置版本、有效期和黑名单。页面区分未自动处理、等待、处理中、已通过、失败、结果待核对及已取消；不确定回执不自动重试。自动通过申请与入群后的活人验证分别处理，已开启的验证规则仍继续生效。首次接入不从历史申请列表补批通过；尚未完成真实新申请的验收时，不应把模拟测试当作真实放人成功。

接口：`GET /api/v1/qq-local` 查看本机登录入口；`GET /api/v1/qq-local/login` 读取二维码及状态；`POST` 子路径 `/refresh`、`/connect` 刷新二维码／登记连接。已有连接对应 `/api/v1/accounts/:id/qq-login`，另有 `/quick` 尝试原账号的已保存登录。群审核使用 `GET/PUT /api/v1/conversations/:id/qq-requests`。均仅限后台管理员，项目密钥不可访问。

依据：[OneBot 加群申请事件](https://github.com/botuniverse/onebot-11/blob/master/event/request.md)、[处理入群请求](https://github.com/botuniverse/onebot-11/blob/master/api/public.md#set_group_add_request-处理加群请求邀请)、[NapCat 登录接口](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-webui-backend/src/api/QQLogin.ts)。

### QQ 入群后的活人验证

在 QQ 群的“管理规则”中开启活人验证，设置 30–3600 秒时限及超时处理。默认“记录超时，由管理员处理”；也可在有发送和移出权限时选择自动移出。入群审核只负责通过申请：收到真实 `group_increase` 通知后，才为这一入群批次建立验证。入群审核页面可查看后续验证进度，群详情“活人验证”和全局“安全与验证”显示完整记录。开启前的老成员不会补发验证，也不会因此被阻止正常同步或报名抽奖。

QQ 验证使用加法题，并 @ 新成员。成员 @ 本机器人后直接发送数字答案，或引用回复该条验证提示并发送数字答案，无需复制指令或验证码；仅本人和当前批次有效，最多回答三次。只识别真实 QQ @ 片段，纯文本伪造 @ 或提到其他人不会触发答题；引用旧题不会验证新入群批次。兼容旧提示中的 `/verify 批次标识 答案` 指令。答对后记录通过并发送确认。群主、管理员和机器人自身不执行自动验证处分。提示取得明确成功回执后才开始倒计时，排队或发送结果不确定不消耗成员的作答时间。

后台区分等待发送、正在发送、发送失败、发送待核对、等待验证、回答次数用尽、超时人工处理、移出排队／处理中／成功／失败／待核对、退群和旧批次。超时人工处理不会踢人；管理员可人工通过或重新发送。重发会更换题目和批次标识，确认送达后重新计时；要求 `Idempotency-Key`，同一请求不会重发多条。发送结果未知时先核对原任务，不能直接重发。

QQ 可分别配置“连续答错 3 次后”的处理：默认转人工，可选禁言 10 分钟；单纯超时仍按独立的超时设置处理。失败禁言使用 [OneBot `set_group_ban`](https://github.com/botuniverse/onebot-11/blob/master/api/public.md#set_group_ban-群组单人禁言)，固定 `duration=600`，只在三次有效错误回答后创建一次任务。执行前重新核对 QQ 身份、实时管理员权限、目标普通成员身份、原入群批次及当前禁言截止；已被禁言或无法核对状态时不覆盖原处分。结果未知不重试；后台分开显示禁言排队、成功、失败和待核对。禁言到期由 QQ 自动解除，人工通过验证不会自动解除已有禁言；需要提前解除时，由管理员在 QQ 客户端核对后处理。

可选自动移出只在验证提示确认送达、实际超时且成员仍属原批次时提交任务。执行前复查账号、群选择、规则版本、实时管理角色及平台入群时间。提示发送失败、账号离线、权限不明或平台入群时间无法核对时交给管理员；已发出动作但没有明确回执时保留待核对，不重复踢人。退群、重新入群、关闭验证或修改验证配置会停止旧任务；仅修改广告关键词不会中断正在进行的验证。移出执行中或结果待核对时不能人工通过来掩盖平台结果。

超时处理还可选择“禁言 10 分钟，到期重新验证并循环”（`verification_timeout_action=mute_retry`）。提示已确认送达且超时后，提交一次 600 秒禁言；取得成功回执后持久保存下一次检查时间。QQ 自行到期解除禁言，后台在约 10 分钟后实时核对成员仍属原入群批次、已解除禁言、机器人身份与权限仍有效，再 @ 成员发送新题。每轮更换题目和标识，重置三次答题机会，确认送达后重新给予完整答题时限。再次超时则继续；开启三次答错禁言时，该禁言也会进入同一循环。服务重启不会丢失等待轮次，不提交主动解禁请求；成员新增了其他禁言、权限不明、发送或禁言结果待核对时停止自动循环，交管理员处理。验证通过、人工通过、退群、关闭验证或改变验证配置／群选择会停止旧循环。后台显示当前轮次、禁言中和预计重新出题时间，各轮任务保留独立回执。

接口：`GET /api/v1/verifications` 和 `GET /api/v1/conversations/:id/verifications` 查看状态与发送／处理任务；`POST /api/v1/verifications/:id/approve` 人工通过；`POST /api/v1/verifications/:id/resend` 重新发送 QQ 验证，需 `Idempotency-Key`。均仅限后台管理员，写入校验 CSRF；不返回答案散列或完整内部验证上下文。

外部 OneBot v11 桥接仍可手动接入：自行运行个人 QQ 客户端，在“QQ · OneBot HTTP 桥接”填写 HTTP 根地址和访问 Token，再刷新群列表与角色。该方式的客户端启动和登录由桥接所在机器负责。

同机 NapCat 可仅绑定 `127.0.0.1:3004`，后台设置 `QQ_LOCAL_PORT=3004`，QQ 连接地址精确填写 `http://127.0.0.1:3004`。此配置只放行该 QQ 回环地址，不需要启用全局 `ALLOW_PRIVATE_CONNECTORS`；HTTP Token 和禁止重定向的检查继续生效。

将创建时返回的 `qq_events_url` 设为 HTTP 上报目标。NapCat 的 HTTP 客户端 Token 填 `qq_webhook_token`，后台按原始请求字节验证其 `X-Signature: sha1=<HMAC-SHA1>`；其他桥接也可携带 `Authorization: Bearer <qq_webhook_token>`。若请求带签名则必须验证通过，不会回退到 Bearer。此上报 Token 与访问 OneBot HTTP 服务的 Token 分开配置。上报 `self_id` 必须匹配已连接账号。只接收已发现群，新加群先刷新。

连接后固定 QQ 身份，执行发送、撤回或移除成员前会重新查询当前登录账号。桥接登录了其他 QQ 时，刷新与执行都会拒绝继续使用原连接；需要恢复原 QQ 或新建连接。

管理角色优先通过 `get_group_member_list` 的 `no_cache=true` 请求核对当前 QQ；仅在列表不可用时尝试同样要求实时数据的单成员接口，不使用缓存角色兜底授权。结果必须同时匹配群号、当前账号及明确的 owner/admin/member 角色。部分 NapCat 环境的强制刷新单成员接口返回失败，而实时成员列表可用；因此该失败不再使有效管理员一直显示未知。普通成员明确显示未授权，无法确认的结果保持未知。发现群权限结束时再次核对登录身份，撤回和移出成员前也会在角色查询后再次核对身份。已发出动作但 HTTP 状态或 OneBot 状态与返回码矛盾时，结果保持待核对。

VPS 的 NapCat v4.18.41 使用受版本散列保护的成员查询修复：强制列表刷新等待原生结果，不读取旧缓存冒充刷新成功；单成员强制查询只使用该群、该 UID 的实时成员事件，校验 QQ 身份和角色，不再等待与权限无关的个人资料查询。空结果、错误角色或身份不匹配仍拒绝授权。补丁生成脚本为 `scripts/patch-napcat-members.ts`，仅识别已核验的原始代码包，输出到新发布目录，保留原始版本；后续升级 NapCat 必须重新检查该修复，不能对未知版本套用。依据：[上游列表查询](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-onebot/action/group/GetGroupMemberList.ts)、[单成员查询](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-onebot/action/group/GetGroupMemberInfo.ts)。

## 管理规则与处理结果

群详情的“管理规则”根据当前执行账号的连接器能力、权限新鲜度、在线和群选择状态禁用不可用动作，并显示原因。删除并移出/封禁同时要求删除消息能力和对应成员管理能力。后端保存接口执行相同检查；不能通过直接请求启用不支持的自动处理。观察模式仍允许保存关键词和域名，但不表示平台具备处罚能力。已有不可用动作可切回观察模式后保存。成员验证需有可用的发消息权限；暂停或取消同步后可先关闭验证再保存。

“平台能力”可刷新当前账号的群权限，并查看已授予、未授予、未知及具体原因。此入口使用 `POST /api/v1/accounts/:id/permissions-refresh`，需管理员会话与 CSRF，不会恢复已暂停账号；恢复连接仍在“连接账号”操作。这里声明的动作可用仍不能替代执行前的成员批次检查；老成员缺少可信入群记录时，移出/封禁会停止。

消息记录和实时聊天分别展示规则判定和实际任务结果：“规则命中”不是“已删除”。每个删除、移出、封禁任务独立显示等待处理、处理中、平台已接收、处理成功、处理失败、结果待核对或已取消；点击结果可查看任务详情。部分成功不会掩盖另一动作失败或待核对，旧消息版本的任务会注明版本。外部删除事件只有删除标记时，不冒充本系统成功回执；演示成功会明确标注。群黑名单不受广告观察模式豁免，仍会为后续发言提交处理任务。

引用消息上报使用 OneBot 消息段数组，保留 `{ "type": "reply", "data": { "id": "原消息ID" } }`；出站回复也按此格式发送。原始 CQ 字符串当前仅作为文本显示，不解析其中的回复标记。依据：[OneBot 消息段](https://github.com/botuniverse/onebot-11/blob/master/message/segment.md)。

## 关键词触发

群详情新增「关键词触发」，与原有广告规则独立。每群最多 50 条，每条最多 100 个关键词；支持包含、整条文字匹配，统一全角半角、大小写与常见零宽字符，不执行正则。每条消息仅执行排序最靠前的第一条启用规则，顺序相同按创建时间和 ID 排序。默认观察模式只记录命中，测试匹配也不产生平台动作。

自动回复和警告支持固定文字、单张 JPG/PNG 及图文，引用原消息并保留 TG 话题。警告仅在发送成功回执后计入 `member_actions`，重复回执不会重复计数。TG 超级群可限时禁言，TG 可封禁，QQ 可限时禁言或移出；删除单独检查撤回权限。TG 和 QQ 由平台按时长解除禁言，不覆盖已有成员限制；币安未开放关键词限时禁言或其他自动处罚。币安警告与管理员豁免要求服务器直连。自定义源仅允许文字回复，需关闭管理员豁免。

只匹配新入站消息的文字或图片说明。历史、编辑、出站回执、带同步 trace 的消息、超过两分钟的积压消息不执行；被广告规则、验证或黑名单拦截的消息优先处理。关键词自动警告或处罚命中也会阻止该消息跨群转发。成员冷却为 5 秒至 24 小时，每条规则另有群内 3 秒间隔，均持久化并在群事务锁下判定。

执行任务有效期两分钟。每次执行检查规则修订、原消息内容版本、原广告/验证策略版本、登录会话、群同步范围、在线与权限快照、黑名单、成员批次、冲突任务；实际发送或处罚前再次检查。处罚始终豁免群主、管理员和机器人。无法实时核对成员、已有禁言、登录身份不符或结果不明时停止并保留原因，不用旧任务补发或重复处罚。规则修改、停用或删除会取消待执行任务，已执行和待核对回执保留。后台分别展示观察、冷却、待执行、处理中、成功、失败、待核对、取消与角色豁免。

管理接口（管理员会话及 CSRF）：`GET/POST /api/v1/conversations/:id/keyword-rules`，`PUT/DELETE .../keyword-rules/:ruleId`，`POST .../keyword-rules/preview`。编辑必须携带读取时的 `expected_revision`，旧版本保存返回冲突，避免覆盖其他操作。接口与页面使用相同的动作可用性限制；观察模式可保留尚不可执行的规则。

## 实时消息与反向代理

`/api/v1/conversations/:id/stream` 使用 SSE，浏览器通过同源管理员 Cookie 鉴权，无需在 URL 中传凭据。每秒读取数据库快照，有变化时推送；每 15 秒发送心跳。注销或会话过期会结束连接，重连后补上最近 100 条窗口内的消息及投递状态。首次显示最近 100 条，网页通过 `GET /api/v1/conversations/:id/history?before=<消息记录ID>&limit=50` 向前翻页。游标绑定逻辑群及消息记录，使用 `(created_at,id)` 排序，避免同一时间消息重复或遗漏。此端点仅接受管理员会话；分页读取后台已保存的消息，不向平台补抓接入前历史。

HTTPS 代理应为此路径关闭响应缓冲和缓存、允许长连接，并把读取超时设为至少 60 秒。例如 Nginx 在对应 location 内设置 `proxy_buffering off; proxy_cache off; proxy_read_timeout 60s;`；服务同时返回 `X-Accel-Buffering: no`。CDN 也需允许流式响应，否则网页更新可能被延迟。连接缓慢且持续无法写出时，服务会结束连接，由浏览器重新连接。

数据库启动时自动添加消息引用与话题字段，现有记录保留。真实平台引用能否成功仍取决于原消息是否存在、当前账号权限及连接器实现；Telegram 引用丢失时不会自动降级为无引用发送。

## 任务与恢复

事件与后续任务在同一事务保存，worker 通过 `FOR UPDATE SKIP LOCKED` 领取。动作前记录 attempt 并检查权限、审核内容和规则。确定失败且 retryable 才允许手动重试，默认不自动重试。

执行超过 2 分钟未确认、或 accepted 超过有效期没有最终回执，会成为 unknown。在“通知与发布 → 全部投递任务 → 详情”查看尝试，并在核对平台实际记录后填写依据。确认成功需提供发送的消息 ID；确认完全未执行后才允许重试。核对依据与状态同事务保存。

连接器也可提交更高 revision 的最终回执。旧回执不覆盖新结果，成功/失败终态不可回滚。重启不会直接重发无法确认的动作。

已连接过的 QQ、币安账号短暂读取失败后，维护任务每 30 秒重新核对连接和权限；管理员暂停的账号不会自动恢复。网页登录或 QQ 会话失效时仍需恢复登录。此检查只恢复连接，不重发结果未知的任务。Telegram 和 QQ 文本发送缺少有效平台消息 ID 时也会进入待核对，不显示“已发送”。

本地超时不生成连接器回执或占用其 revision。任务/尝试可以是 unknown，同时 receipt 为空或仍保留最后一份 accepted；调用方以任务 status 判断是否完成。迟到的合法最终回执仍可结案。

乱序旧编辑不覆盖新内容；时间相同但内容冲突进入待核对。先收到删除事件时保留删除标记，后到的原消息或编辑不会重新进入同步。验证挑战发送前重查当前批次与有效期。

PGlite 同一目录只允许一个进程，`postgres.lock` 防止并发打开。正常退出释放锁。崩溃后查看锁里的 PID，确认进程已结束再删除锁，不能在运行中移除。多个服务实例使用外部 PostgreSQL，同一个 Telegram Bot 仍只运行一个轮询接收器。

## Docker 与备份

已有 Node.js、PostgreSQL 和 Caddy 的 VPS 可直接使用 [VPS 部署指南](vps-deployment.md)，无需为运行 Chrome 的电脑申请公网 IP。

提供 `Dockerfile`、`compose.yaml`。当前机器没有 Docker，容器启动尚未验收；原生 Node、PGlite、HTTP 以及 VPS 上的 PostgreSQL 16、HTTPS 与实时连接已验证。

在环境或 `.env` 配置 `POSTGRES_PASSWORD`、`ADMIN_SETUP_TOKEN` 和 64 位十六进制 `ENCRYPTION_KEY`，再运行：

```sh
docker compose up --build -d
```

默认只映射本机 `127.0.0.1:3000`。正式部署通过自己的 HTTPS 反向代理，设置真实 `PUBLIC_ORIGIN` 和 `COOKIE_SECURE=true`。

本地模式正常停机后备份整个 `DATA_DIR`，含数据库与 `master.key`。外部 PostgreSQL 用原生备份，并单独备份加密密钥与配置。数据库和密钥恢复时必须匹配。`.env`、密钥、本地数据禁止提交 Git。

## 图片、头像与群选择

TG 图片保存文件标识并通过 `getFile` 获取临时下载地址；QQ 保存消息段图片资料，并通过原消息 ID 刷新可用地址。图片和头像经后台管理员接口输出已验证的图片字节，限制 HTTPS 公网目标、大小和响应时间；不输出 TG Token、Cookie 或本地文件路径。TG/QQ 老消息没有文件资料时可能无法恢复图片，界面显示失败提示并允许重试。头像缺失或隐私限制时显示默认图标。

QQ 图片优先读取仍有效的已存链接；失效后核对原群、原消息和发送人，再尝试 `get_msg` 的更新链接。桥接重启后若短消息 ID 映射丢失，只在原群中最多读取 3 页、每页 100 条历史来恢复定位，不补入业务消息或触发规则，仍须精确匹配消息与发送人。若上游仍返回过期的旧版 qpic 链接，使用该原消息返回的受限图片标识调用 `get_image`，取得更新下载地址。拒绝将任意 URL 或本地路径当作图片文件标识，也不读取接口返回的服务器文件路径。整个过程限时 20 秒，成功字节缓存 5 分钟、总量最多 16 MiB，并合并相同图片的并发读取；缓存仍需通过账号、群同步范围、消息删除与图片版本检查。原消息已删除、超出可恢复历史范围或上游无法恢复时明确显示读取失败，不把错误页当图片。该缓存不替代持久图片归档。依据：[NapCat 原生图片下载](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-onebot/action/file/GetFile.ts)、[内存中的消息 ID 映射](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-common/src/message-unique.ts)。

QQ/TG 的管理员群选择接口为 `GET /api/v1/accounts/:id/groups`、`POST /api/v1/accounts/:id/groups/refresh`、`PUT /api/v1/accounts/:id/groups`。保存体为 `{ "group_ids": ["平台群ID"], "revision": "读取时的版本" }`，并发旧版本会拒绝保存。首次保存前保留当前范围；保存后新发现群不会自动启用。取消同步会取消该群尚未执行的任务、阻止新事件和新投递，并保留历史及结果未知的任务。Telegram 的群清单来自已发现/手动登记的群。

任务入队在事务中持有账号范围的共享锁，与取消同步串行生效，避免取消后留下遗漏的待发任务。失败任务重试也需检查群仍在同步范围内；重新勾选群不会复活已取消的任务。

群发 `POST /api/v1/announcements` 支持管理员 `Idempotency-Key`。同一键和相同内容/群/时间返回同一个发布 ID，更换载荷返回冲突；网页在网络重试时沿用请求键。创建任务前校验选中群仍在同步范围内及平台文本长度限制，执行时再次检查权限与范围。

## 图片与图文群发

管理员使用 `POST /api/v1/uploads/images` 上传图片原始字节，携带正常管理员 Cookie 和 CSRF 头，返回图片 ID、类型、大小和尺寸。只接受 JPG / PNG，最大 8 MiB，校验文件头及尺寸；图片宽高之和最大 10000，宽高比最大 20。重复上传相同字节复用图片 ID。`GET /api/v1/uploads/images/:id` 也需管理员会话，返回私有、不可缓存的图片字节。无需开放公共图片 URL 或服务器文件路径。

发布体可带 `image_asset_id`，`content` 可为空表示纯图。单张图片加说明作为一个平台消息发送：TG 使用 `sendPhoto` 的 multipart 文件与 caption（最大 1024 字符），QQ 使用 OneBot 的文本/图片消息段并传受控 base64，币安 v0.1.8 走官方群图片上传与真实回执。平台、说明长度、图片存在性、币安桥接版本及群范围校验失败时，整批不创建任务。定时、幂等键、取消待发及结果核对继续有效；图片字节保存在 `uploaded_images`，数据库备份也包含这些图片。

实时消息快照与初始列表都过滤取消同步的群，QQ、TG、币安行为一致。正在查看的群取消同步后跳转到其他启用群；全部取消后显示空列表。群详情仍能查看保留历史。

实时快照携带数据库读取时间 `observed_at`，用于排除晚到的旧 HTTP 快照；所有已访问群的缓存共享最新同步群列表，切回旧群不会恢复已取消的群。历史分页与消息缓存继续保留。读取时间本身不触发 SSE 推送，内容或权限发生变化时才推送新快照。

图片上传或替换失败时，网页禁止创建发布任务；重新上传成功或明确移除图片后才可继续，避免把替换前的旧图误发出去。

## 管理台日常操作

顶部搜索或 `Ctrl / ⌘ + K` 可查找页面、群名称和群 ID。实时消息按平台筛选，群内查找仅覆盖已加载的消息；查找更早记录前先加载历史。图片可原位预览，按 Escape 关闭。切群会保留各群阅读位置，准备新群期间暂时锁住编辑与发送。

聊天文字草稿按管理员账号隔离，保存在当前浏览器标签页的 sessionStorage，最多保留最近编辑的 30 个群，不上传服务器。提交期间会一并保留发送请求及引用信息，刷新后原样重试复用同一次提交；主动修改正文或引用后视为新消息。旧发送回执不会清空新编辑的草稿。浏览器存储不可用时仅保留当前页面内存草稿，并显示刷新前复制的提示。

群目录支持平台、同步范围和关键词组合筛选，筛选写入 URL；群详情的消息、规则、审核和验证标签也可直接打开。规则编辑显示未保存状态，支持还原，未修改时不提交保存。同步群选择支持批量操作、仅看已选；刷新发现列表保留未保存的勾选，仍须点击保存才生效。如果其他页面已更改同步范围，先提示冲突并阻止覆盖，点击“载入最新勾选”后再重新调整。

群发提供内容预览、目标平台统计与动态字数上限。立即发送要求目标账号在线；定时任务可选择当前离线的目标，但需要在执行前恢复连接。网页定时输入统一按北京时间（UTC+8）解析，与设备所在时区无关。发布和投递筛选基于最近 100 条记录；失败、待核对和执行中分别显示。已过期或 QQ 验证专用任务不展示普通重试入口，后者需回到活人验证页面处理。
